A1 语义化行程搜索与智能撮合

★★★★★
真实产品功能官方文档
功能是什么：用户在助手/搜索框说自然语言软需求（"周五18点从石家庄去邯郸、能带大件行李、最好离地铁近"），系统自动抽结构化查询（时间窗/起终点/行李偏好/上车点偏好），走 ES 召回→多特征排序→TopN 行程，并解释"为什么这几单推荐给你"。
用户真会用吗（需求证据）：
  • 真实产品功能哈啰顺风车 2026-04 行业首创开放 MCP：车主匹配、路线规划、价格计算、差异化筛选（宠物友好、豪华车）等核心能力以标准化接口开放给 AI 模型——AI 调用撮合能力就是行业当下方向。
  • 官方文档嘀嗒《订单匹配规则》：匹配核心特征是"车主接乘客的额外绕路距离"和"乘客/车主里程比"两个可量化特征——撮合排序是特征工程问题，个人项目可 mock 复刻。
  • 真实产品功能嘀嗒"附近最优"上车点推荐：按匹配效率、步行距离、顺路车数、价格综合打分——"综合打分＋解释"形态已被验证。
  • 真实产品功能嘀嗒车主侧常用路线×8、途经点、顺路自动抢单、关注行程相似自动提醒（2026-05）。
技术怎么实现：不是纯 LLM。NL→结构化走 LLM function calling 抽取，高频句式走规则模板（复用现有三层漏斗）；召回复用 trip-service 已有 ES（IK 分词＋行程索引）动态组装查询 DSL；排序特征＝时间匹配度、直线距离近似绕路、车主信任分/评分、余座数；解释层把命中特征转成一句话（"这班车主路线与你重合度 92%，且信任分 4.8"）。
工作量与依赖：3–4 人日（NL 抽取工具 1d＋ES 动态 DSL 与排序服务 1.5d＋解释生成与前端展示 1d）。零付费 API，LLM 可插拔（Ollama 本地），天气/地图均不需要；200+ 条往返石家庄/邯郸虚拟行程种子数据即可演示。风险：ES 动态 DSL 组装注意注入与语法边界。
简历讲点：后端——两阶段召回（粗排 ES filter→细排特征打分）、动态查询 DSL 组装、热门路线多级缓存（Caffeine+Redis）、特征计算并发（CompletableFuture 并行取信任分/余座）、Sentinel 限流保护 ES；"为什么推荐"＝决策可追溯。测开——NL 解析 golden 集（50 条口语样例→期望结构化条件）算抽取准确率；排序特征边界单测；Mock LLM 测 function calling 参数；召回率/排序位置评估脚本。
与六场景衔接：不重复，双边互补。新增意图 semanticSearch 挂在三层漏斗 LLM 层；复用 trip-service 的 ES 搜索与行程详情接口；与场景1 queryTrip 共用行程数据底座。

A2 智能取消挽留与退改费用解释

★★★★★
官方文档真实产品功能社区讨论推断
功能是什么：用户说"明天去不了了/时间太赶想改晚上"时，助手不直接执行取消：①识别取消/改签意图与原因 → ②按规则实时算判责与违约金（距发车时间窗）→ ③给替代方案（改时间可行班/换其他车主/先上候补）→ ④把"扣多少钱、退到哪、多久到账"用人话讲清楚，用户确认后才执行。
用户真会用吗（需求证据）：
  • 官方文档嘀嗒《顺风车取消规则》《乘客有责取消判责规则》：市内订单出发前 15 分钟、城际 2 小时保护期内取消收补偿金，30 分钟索赔窗口，未索赔全额退回。
  • 真实产品功能嘀嗒：乘客和车主取消时均需选择取消原因，系统自动判责并对有责方惩罚（扣信任分/取消次数/补偿金）。
  • 社区讨论哈啰规则媒体实测：出发前 15 分钟前取消双方无责，之后有责方被同时扣当日取消次数、信任分、取消费——三家规则各不相同，用户搞不清"现在取消亏不亏"是真实吐槽点。
  • 官方文档12306 候补：最多 6 个候补订单、每单最多 60 个车次、可"接受临时新增列车"——"没车时用候补兜底"是国家级产品验证过的范式。
  • 推断"取消前给替代方案挽留"在顺风车 App 内未见明确官方功能名，属对现有判责能力的 AI 增值层。
技术怎么实现：规则为主、LLM 只做话术。违约金/判责＝纯规则引擎（复用 order-service 订单状态机已有取消逻辑，按时间窗分档：保护期内免费/接近发车档扣 X%），LLM 不参与算账；替代方案＝复用现有查询：查同路线可用行程（改时间）、查候补队列状态。
工作量与依赖：2–3 人日（取消挽留对话流状态机 1d＋判责规则与违约金计算复用/收口 0.5d＋替代方案查询串联 0.5d＋LLM 话术模板 0.5d）。无付费 API；判责规则可自定分档（对齐嘀嗒：城际提前 2 小时无责）。演示把系统时间拨到"发车前 1.5 小时"即可展示扣款分档。风险：挽留流程防重复触发幂等（同一订单挽留状态只推一次）。
简历讲点：后端——取消判责状态机（无责/部分有责/有责×时间窗矩阵）、违约金计算规则链、挽留流程幂等（Redis 标记"已挽留"）、延时消息（用户犹豫超时自动二次提醒）、与支付退款链路衔接。测开——全组边界用例最密集：时间窗临界点（提前 2 小时整 vs 1 小时 59 分）、保护期内外、30 分钟索赔窗口边界、重复取消幂等、并发取消与占座释放竞态；"是否算错钱"做规则断言兜底而非 LLM 自评（一票否决项）。
与六场景衔接：不重复，是现有场景2（queryOrder/cancelOrder）的前置增值层。在 assistant-service 拦截 cancelOrder 意图，先走挽留子流程，用户确认后才调既有 cancelOrder function；与 FAQ 互补——FAQ 讲通用规则，A2 讲"你这单现在取消具体扣多少"。

★★★
官方文档真实产品功能社区讨论推断
功能是什么：下单前自动穷举"可用券×拼车满座折扣×是否候补"的组合，算全局最省方案（含互斥校验、金额边界），直接告诉用户"你这单用 A 券＋接受拼满座能省 12.5 元，候补成功率 80%"，LLM 只负责把结论写成推荐话术。

★★★★

功能是什么：行程结束双方互评后，把自由文本评语（如"师傅很准时，车内也干净，就是话有点少"）用 LLM 抽成结构化标签（准时/迟到/绕路/车内整洁/话少/好沟通/吸烟…），标签加权汇入信任分，并在用户主页生成一句评价摘要；标签在行程撮合/排序时作为展示与筛选因子。
用户真会用吗（需求证据）：

工作量与依赖：2–3 人日（标签词表+抽取 prompt 1d；信任分加权规则与入库 0.5d；摘要+前端信息卡展示 1d）。外部依赖无；LLM 走可插拔通道。脚本造 100+ 条互评文本，演示展示"输入一段话→右侧自动冒出标签→信任分变化"。
简历讲点：后端——①评价事件驱动：行程完成事件进 MQ，异步消费做标签抽取，不阻塞评价提交接口；②幂等与防刷：同一条评价只抽一次（去重表），短时间大量评价用 MQ 削峰＋消费限流；③信任分读多写少，走 Caffeine 本地缓存＋Redis，标签聚合查询走 ES 或预计算；④抽取失败进死信，不影响主流程。测开——"评语→期望标签"标注集做准确率/召回率回归；Mock LLM 测信任分加权边界（正负标签、时间衰减、幂等）。
与六场景衔接：与现有六场景（前台对话）不重复。但与原方案§四"信任分：双方互评→信任分→影响展示排序"已有雏形——B2 不是从零做信任分，而是把原来可能靠"星级/布尔项"的互评升级为"自由文本→LLM 抽标签→加权信任分→摘要展示"，是对已有模块的 AI 增强，衔接自然、增量清晰。

B3 接口用例自动生成＋AI 助手评估平台

★★★★
社区讨论开源项目
功能是什么：两件事：①从项目自己的 OpenAPI（Knife4j 导出）定义自动生成 REST 接口测试用例与断言（happy path/边界/异常）；②面向 AI 助手本身，构建意图 golden 集、工具调用成功率/准确率评估与回归流水线——即"测 LLM 系统的测试平台"。注意形态：这是 CI 里跑的工程质量平台，不是面向用户的产品功能。
用户真会用吗（需求证据）：
  • 社区讨论论文《RESTifAI: LLM-Based Workflow for Reusable REST API Testing》（ICSE 2026 Demonstration track 录用，生成可执行 Postman collection）；APITestGenie（从业务需求+OpenAPI 用 LLM+RAG 生成 API 集成测试，在 10 个真实 API、约 1000 endpoint 上验证）。

  • 社区讨论TesterHome 上的 ai_test_agent：需求文档驱动并行生成用例、异步后台生成＋WebSocket 进度推送。
技术怎么实现：①接口用例生成：解析 Knife4j/OpenAPI JSON → prompt 喂入（路径、入参 schema、出参 schema、错误码）→ LLM 输出结构化用例 {case_name, method, path, headers, body, expected_status, assert_fields} → 转成 REST Assured 可执行脚本；断言三类：状态码＋关键字段非空＋边界值。②评估平台：人工标注 50–100 条对话样本（用户 query、期望意图、期望调用 tool name、期望槽位）→ 批量推理脚本，指标＝意图准确率、工具调用成功率、参数正确率；LLM 可 Mock 也可真跑，差异即回归，结果入库。
工作量与依赖：4–6 人日（OpenAPI 解析+用例生成模板 1.5d；用例转可执行+断言校验 1d；golden 集标注 50–100 条 1d；评估脚本+CI 集成+报告页 1.5d）。无新中间件；OpenAPI 来自自己工程，golden 集自己标注；评估脚本本身就支持 Mock LLM（这正是它的测开价值）。
简历讲点：测开（主）——①评估集设计：如何分层标注、如何避免数据泄漏；②Mock LLM 单测——不依赖真实 LLM 也能测三层漏斗路由逻辑；③断言设计（状态码/字段/边界/幂等）；④回归门禁——golden 集分数下降即 CI 红灯；⑤补上已有 JMeter 之外"LLM 侧质量"这块空白。形态是 GitHub Actions CI 流水线＋后台趋势看板（意图准确率/工具调用成功率趋势），不要包装成 C 端功能。后端（次）——用例生成服务本身是个小后端（接收 OpenAPI、异步生成、进度查询 WebSocket），能讲 MQ 异步、任务状态机、限流。
与六场景衔接：不与前台六场景重复。但与原方案§三/§七已规划的"意图 golden 集准确率、工具调用成功率（Mock LLM）、LLM 评估脚本"高度重叠——B3 的真正增量是把已规划的评估从"一个脚本"升级为"平台化：用例自动生成＋CI 门禁＋趋势看板"。直接在原测试体系里落地，不另起炉灶。

B4 FAQ 自动挖掘与 RAG 自更新

★★
官方文档开源项目推断
功能是什么：定时/事件驱动地从已解决工单、转人工会话中挖掘高频重复问题，让 LLM 提炼成标准 FAQ 条目（问题+标准答案），人工审核后入 FAQ 表并重建向量索引；同时对现有 RAG 的切分质量与召回命中率做评估（Recall@K/MRR）。
用户真会用吗（需求证据）：
  • 官方文档实在智能"智能客服知识库自愈闭环"：自动感知对话/工单中的知识缺失信号→诊断→简单自动修复、复杂内容人工审核→效果验证。
  • 开源项目ZBrain FAQ Generation Agent：分析 Zendesk/JIRA 已解决工单，用 LLM 抽取 Q&A、合并重复条目、优化已有 FAQ。
  • 官方文档AWS 博客：Support Case 问答系统从 Support API 定期取最新 Case 自动更新知识库；My AskAI 区分 RAG（运行时检索）与 self-learning（知识体长出来）。
  • 推断个人项目不上线，工单数据是 mock 出来的几十条，"自动挖掘高频问题"在演示时挖不出真实痛点。
技术怎么实现：XXL-Job 定时扫"已闭环工单"→ LLM 聚类相似问题＋抽 Q&A 对 → 与现有 FAQ 表做向量相似度去重（>0.9 判重）→ 进待审核队列 → 后台人工确认 → 写 FAQ 表＋pgvector 重建索引；召回评估构造 30–50 条 query 标注正确文档，测 Recall@K/MRR 对比不同切分策略。
工作量与依赖：3–4 人日。外部数据无，用自己工单表；需向量库（现有 RAG 已具备）。风险：与现有场景⑥（FAQ RAG）共享同一知识库，增量薄。
简历讲点：后端可讲定时任务、向量重建、去重相似度判断——但这些点在项目里已有更重的场景（ES 同步、RAG），边际增量小。测开——RAG 召回评估（Recall@K/MRR）是相对新的点，但体量小。
与六场景衔接：与现有场景⑥（规则/费用/退款 FAQ，RAG）重复度最高：FAQ 表、向量库都已存在，B4 只是把 FAQ 的"录入方式"从手写改成"自动挖掘"。若保留，缩成一个 XXL-Job＋一个后台"待审核 FAQ"小队列即可，不必独立成大功能。

B5 安全/紧急意图识别

★★★★
真实产品功能社区讨论
功能是什么：在 AI 助手对话（及乘客-司机会话文本）中识别高风险意图——"我被困车上了/司机绕路不停车/被骚扰/我要报警"——一旦命中，立刻中断普通对话流，自动触发紧急流程：行程实时位置/路线展示给紧急联系人、模拟拨打 110、弹窗安全指引、人工客服加急介入，并给该行程打安全标记。
用户真会用吗（需求证据）：
  • 真实产品功能滴滴紧急求助（2016 年上线）：按下后上传实时录音、客服监听回拨、自动发送行程信息给紧急联系人、可一键拨 110/120/122；2019 顺风车复线即带 110 报警、行程分享、路线偏移提醒。
  • 真实产品功能滴滴安全 AI 模型（2026 官方公布）：多模态风险研判大模型融合 NLP、订单异常、行程动态做风险初筛，高危行程自动触发远程外呼、安全警示、紧急报警处置，"AI 初筛+真人复核"。
  • 真实产品功能T3 出行：行程对话中"高风险语义"词汇触发车机端语音警示（如"能不能请你吃宵夜"即被判高风险）。
  • 社区讨论论文：Whisper 转写＋微调 DistilBERT 做实时言语骚扰检测，准确率 93.8%。
技术怎么实现：分层——规则层先行：高危关键词/正则（报警、被困、骚扰、绕路、不停车、救命）直接命中零 token，安全场景宁可误报不可漏报，规则兜底；LLM 层：规则未命中但语义模糊的句子（如"他好像不太对劲""路线不对"）交给 LLM 做风险分类 {risk_level: high/medium/none, reason}；处置：命中 high → 不走普通 function calling，走独立紧急通道——写安全事件表、推送紧急联系人（行程分享页）、弹"模拟 110"按钮、转人工队列最高优先级、客服工作台红色弹窗。只做文本意图分类，不做语音识别。
工作量与依赖：2–3 人日（高危词表+分类 prompt 1d；紧急流程编排：安全事件表+行程分享推送+人工加急 1d；前端演示弹窗 0.5–1d）。外部依赖无；行程分享原方案已规划（"行程分享紧急联系人、一键报警模拟"），B5 是给它加一个"AI 自动触发"入口。演示时对着助手说"司机把车开到偏僻地方了，我好害怕"，观察系统从普通聊天瞬间切到红色紧急界面。
简历讲点：后端——①紧急通道与主对话链路隔离：Sentinel 对普通限流，但紧急事件走单独高优先级队列/线程池，不被高峰流量拖死；②事件驱动：命中即发 RocketMQ 事务消息，保证"推送联系人+落安全事件表+转人工"最终一致；③降级：LLM 服务挂了，规则层仍必须能兜住高危词，安全功能不能依赖 LLM 可用性；④安全事件单独埋点/Skywalking tag。测开——安全误报/漏报是核心质量指标：构造对抗样本集（正常抱怨"绕路了" vs 真正危险"被困"）评估分类准确率与召回，漏报率必须压到极低。
与六场景衔接：不重复：六场景都是办事，B5 是兜底安全。与原方案§四已有的"行程分享紧急联系人、一键报警（模拟）"衔接——原来那两个是用户手动点的按钮，B5 增加"AI 在对话里主动识别、自动拉起同一套紧急流程"，把手动功能升级为主动安全，叙事完整。

四、推荐组合（4 组，构成固定）

组合一「后端技术向」——把后端硬核点铺满

包含：A1 语义化行程搜索与智能撮合 ＋ B1 客服工单智能分派+会话摘要+回复草稿 ＋ B5 安全/紧急意图识别。

技术闭环：A1 产出检索与排序链路（查询改写/两阶段召回/缓存）；B1 消费已有"转人工队列"事件走 MQ 异步，并做限流降级与 token 成本控制；B5 用规则前置拦截做零 token 兜底与独立紧急通道——三者分别落在"读多写少的检索""异步后台增效""高优隔离通道"三种后端经典问题上。

面试怎么讲：后端岗——"ES 两阶段召回＋MQ 异步坐席摘要＋紧急通道高优隔离，限流降级全链可观测。"测开岗——"NL 解析 golden 集＋分派规则 mock 单测＋安全对抗样本召回评估。"

风险与代价：工作量合计约 8–12 人日（3–4＋3–5＋2–3）。最可能翻车的点：B1 后台工作台 UI 耗时超预期；LLM 摘要质量在演示现场波动——用固定 demo 对话兜底。

组合二「测试开发向」——把测开作品集立起来

包含：B3 接口用例自动生成+AI 助手评估平台 ＋ A2 智能取消挽留与退改费用解释 ＋ B2 评价文本→信任标签抽取+评价摘要。

技术闭环：B3 是 CI 里跑的 golden 集/工具调用成功率/mock LLM 回归流水线（注意：它是"工程质量平台"而非用户可见功能）；A2 的退改规则可写边界断言用例（时间窗/判责/金额精度）；B2 的标签抽取结果可做断言集——评估平台测的正是 A2、B2 这两个功能的 LLM 输出质量，形成"被测对象→评估集→CI 门禁"闭环。

面试怎么讲：后端岗——"OpenAPI→用例异步生成服务，任务状态机＋WebSocket 进度＋CI 门禁。"测开岗——"golden 集意图准确率门禁＋退改时间窗边界断言＋标签抽取回归集。"

风险与代价：工作量合计约 8–12 人日（4–6＋2–3＋2–3）。最可能翻车的点：golden 集标注量（50–100 条）被低估；B3 没有 C 端演示画面，答辩要会讲 CI 看板趋势图。

组合三「演示效果向（答辩 3 分钟）」——观众看得懂的炸点

包含：A2 智能取消挽留与退改费用解释 ＋ A4 行程须知卡片自动生成 ＋ B5 安全/紧急意图识别。

技术闭环：观众能看懂"算钱＋给替代方案"（A2：用户说不去了，助手先算扣款再给改时间选项）；A4 生成图文卡片有视觉冲击；B5 说"我要求报警"直接触发紧急通道（普通聊天秒切红色界面）——一个讲理、一个好看、一个震撼。

面试怎么讲：后端岗——"取消判责状态机＋延时任务触发须知卡片＋安全事件事务消息最终一致。"测开岗——"时间窗临界点断言＋卡片完整性校验＋漏报率压到极低的对抗集。"

风险与代价：工作量合计约 5.5–8 人日（2–3＋1.5–2＋2–3）。最可能翻车的点：A4 卡片前端视觉效果依赖设计感；整套演示全靠"算钱"和"红色紧急界面"两个炸点撑住。

组合四「最低成本保底（3–4 人日）」——两天可上线演示

包含：A3 优惠组合与省钱建议 ＋ A4 行程须知卡片自动生成。

技术闭环：两者都是对已有数据（券/价格/订单/天气）的再加工，不新增外部链路：A3 复用已有券引擎做离线试算，A4 复用通知模块的延时消息与已有天气链路——技术风险最低。

面试怎么讲：后端岗——"试算与实付共用一条规则链保证一致性，算价结果短缓存＋推送频控。"测开岗——"券互斥/门槛/精度边界用例集，直接复用作结算引擎测试展示窗口。"

风险与代价：工作量合计约 3.5–4 人日（2＋1.5–2）。最可能翻车的点：试算价与实付价不一致穿帮（必须共用规则代码）；技术叙事最薄，只适合作为时间不够时的保底方案。

五、不建议做的与理由

A5 一键生成"求拼车"分享文案（建议砍掉）：真实产品分享的是行程卡片/邀请链接（带状态、可直接接单），"AI 生成营销文案"这个形态未找到真实产品对应；纯 LLM 一个调用就完，后端讲不出并发/缓存/幂等任何硬核点，测开无边界矩阵，且个人项目不上线、文案无传播出口。若舍不得，降级为场景4 guidePublish 或 A4 卡片的附属按钮，不单列。
B4 FAQ 自动挖掘与 RAG 自更新（建议砍掉/最小化）：与现有场景⑥（FAQ RAG）共享同一知识库，FAQ 表与向量库都已存在，重复度最高；个人项目工单是 mock 出来的几十条，"自动挖高频问题"演示时挖不出真实痛点，会变成"跑了个定时任务、生成两条 FAQ"。可保留为一个 XXL-Job＋后台"待审核 FAQ"小队列，一句话带过即可，不投入独立开发量。

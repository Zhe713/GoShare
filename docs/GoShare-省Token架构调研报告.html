01

旧方案为什么不继续用先划清界线，新方案才不会被写成旧方案的翻版

上一版 GoShare 的 AI 助手沿用了 ai-doc-lint 的做法。它对「文档问答」有效，但对这个项目有三个硬伤：一是本地嵌入模型要额外内存和启动时间，个人电脑跑微服务已经很紧张；二是重排只提升相关性，不省调用次数；三是三层漏斗的关键词规则要人肉维护，新问题一多就漏。本次要换的是整套思路，不是换一个向量库。

维度旧方案（ai-doc-lint，本次要避开）新方案的方向
核心目标从大量文档里找对片段，提升召回与相关性同样的问答重复出现时，少调用、少传上下文
主要手段本地向量嵌入 + 重排 + 关键词规则漏斗 + pgvector问题指纹版本化缓存 + 免费小模型先行（自检不过才升级）+ 固定前缀白蹭厂商缓存 + 工具结果字段白名单 + 统一网关记账
额外依赖本地嵌入模型、pgvector 扩展、重排模型无本地嵌入模型、无 pgvector、无重排器；只多几张普通 MySQL 表（t_llm_call_log 等）和 Caffeine 内存缓存，零额外容器
触发条件每次请求都走一遍检索链请求先过缓存与路由两道关，命中即结束；只有未命中、自检不过的请求才真正花钱调模型
省不省 token几乎不省：检索完照样把片段塞进 prompt直接省：命中请求的输入输出 token 全为 0；未命中请求靠滑动窗口和字段白名单把输入钉在约 1800 token，再叠前缀命中按 1 折计费

本次设计的三条原则

① 先便宜后贵

每个请求先问免费或几分钱的小模型（GLM-4.7-Flash 免费档），自检不过才升级贵模型；升级只允许一次，不允许两个模型来回跳。便宜答案和贵答案质量接近时，永远先交便宜的那份。

② 能不调就不调

答案能从缓存池、预计算池、模板库里直接读的，一律不进模型，连大模型的门都不让它碰。带实时数据的问题（「我的订单到哪了」）是例外，走实时但只回写不查询。

③ 每一笔都记账

每次调用记录场景、模型、input/output token 和花费，token 一律取响应 usage 字段、不用本地估算。没有记账的「省了多少」在面试里等于没说。

1

问过的问题直接答（语义缓存）

QuestionCacheService · 代表项目 GPTCache
推荐
一句话原理

用户问题先算一个指纹（归一化哈希为主、便宜 embedding 相似度为辅），和缓存里历史问答比一比；超过阈值就把上次给过的答案原文返回，完全不碰大模型；没命中才去调模型，调完把「问题指纹 → 答案」带版本号写回缓存。

省多少

机制：命中请求的输入和输出 token 都为 0，只付一次极便宜的指纹计算；GPTCache 官方论文称命中时响应快 2–10 倍。公开数据

量级：拼车 FAQ 类问题天然高频重复，推断命中率 30%–60%，演示集 warm-up 后可冲 80%+；命中率 50% 时整体 LLM 费用约省 40%–50%，80% 时省 75%+。推断

Java 怎么落

库/组件：Caffeine 存答案原文 + LRU 淘汰（上限 1000–2000 条、TTL 7 天）；条目少于 2000 条时内存暴力余弦即可，不引 FAISS、不引 pgvector。

要不要额外服务：不要。指纹相似度走 OpenAI 兼容接口调几分钱的 embedding 接口即可，不要为它装本地 bge 模型。

关键设计：缓存 key = 模型名 + 功能域命名空间（模型升级后旧答案整体失效）；相似度阈值起步 0.90，上线前拿 20–30 组「同义改写 vs 形近义反」标注对校准；带实时数据的问题只回写不查询。

与旧方案的区别：旧方案向量里存的是「文档切片」，命中后取出片段拼 prompt 再调一次 LLM，路径上还有 reranker 重排；这里比的是「用户问过的问题 + 给过的答案」，命中直接返答案原文，路径上没有重排、不进 pgvector。如果只是把 bge 换成别的向量库、检索完照样拼 prompt 调模型，那仍是旧方案同类，慎用——面试官一眼能看出和上一个项目是同一套东西，简历没有增量。

可行性

外部依赖只有一个 embedding 接口（有免费额度），不要 GPU、不要向量数据库；测试时指纹计算和大模型都用接口替身，本地一条 Redis 都不用起。Caffeine 纯内存、重启丢缓存——演示项目正好用来展示「冷启动 miss → 回热后 hit」。

怎么测
  • 同一句话问两次：第二次模型调用次数 = 0，返回答案一致。
  • 意思相反的两句话不串答案：「怎么取消订单」与「订单如何取消」判命中，「允许拼车」与「禁止拼车」判不命中。
  • 阈值边界：构造 0.89 / 0.91 两组指纹，断言 0.89 miss、0.91 hit。
  • 缓存写满：上限 1000 条时最久未访问的被 LRU 淘汰；TTL 过期后重新调模型并回写。
  • 命名空间隔离：换模型后旧条目不命中。
坑
  • 误命中：触发条件是阈值低于 0.85、形近义反问题多；后果是把「禁止拼车」答成「允许拼车」，涉及钱和规则类问题直接答反；防法是阈值不低于 0.85，钱/规则类问题宁可 miss。
  • 阈值拍脑袋：触发条件是不拿标注对校准就上线；后果是命中率惨淡或误命中频发，缓存形同虚设；防法是上线前用 20–30 组标注对校准一次。
  • 模型升级后答案过期：触发条件是缓存 key 没带模型名和数据版本；后果是把旧模型答案当新模型答案吐出去（面试高频追问点）；防法是 key = 模型名 + 功能域 + 数据版本号。
  • 多轮对话不能缓存：触发条件是把依赖上文的问答塞进缓存；后果是答案缺上下文、被截断；防法是只缓存单轮 FAQ，多轮走实时。

简单题小模型做（模型分级路由）

ModelRouterService · 代表思想 RouteLLM / FrugalGPT
推荐
一句话原理

不是所有问题都配得上大模型。先用规则把问题分流，简单问题直接交给便宜小模型答；小模型答完做一次自检（输出必须是约定 JSON、字段齐全），拿不准的再升级调用大模型。思想源自 RouteLLM（按 query 走强模型还是弱模型）和 FrugalGPT（LLM 级联）。

省多少

机制：把原本 100% 打给大模型的请求，切一部分给便宜 5–10 倍的小模型，只有小模型心虚时才升级一次。

量级：RouteLLM 相比全程 GPT-4，MT-Bench 成本降 85%+、MMLU 降 45%、GSM8K 降 35%，同时保住 GPT-4 约 95% 的表现。公开数据 FrugalGPT 级联最高省 98% 即可追平 GPT-4 单模型表现。公开数据 本项目推断：70% 走小模型、30% 升级，单价差按 10 倍计，成本 ≈ 0.7×0.1 + 0.3×1 = 0.37，省约 60%；演示场景升级率压到 20% 时省约 70%。推断

Java 怎么落

库/组件：配两个 ChatModel Bean（cheap = GLM-4.7-Flash 免费 / qwen-turbo；strong = deepseek-v4-pro），ModelRouterService 编排，基于 Spring AI ChatClient 或 LangChain4j AiServices。

要不要额外服务：不要。不跑 RouteLLM 本体（它是 Python 训练的路由器，个人项目没有标注数据可训），借思想手写规则路由器——这反而更好讲：「参考 RouteLLM 的分流思想，用规则 + 自检实现了等价级联」。

关键设计：升级判定三选一且全部免费——规则前置（难词表）、JSON Schema 校验、模型自报置信度标记；升级只发生一次；强模型超时/报错时降级返回小模型答案兜底。

可行性

零 GPU，路由器就是 if/else + 一次小模型调用；两个模型 API 都有免费额度，演示成本接近 0 元；WireMock 起两个假 endpoint 分别返回「小模型答案 / 大模型答案」，测试不花一分钱。

怎么测
  • 简单问题只调小模型：cheap 调 1 次、strong 调 0 次。
  • 难问题直接走强模型：含触发词/超长时 cheap 0 次、strong 1 次。
  • 小模型 JSON 不合法：cheap 1 次 + strong 恰好 1 次，无二次升级。
  • 强模型超时：兜底返回小模型答案，接口不报错。
  • 路由分布：一组混合问题下，升级率落在配置区间（如 20%–40%）。
坑
  • 静默答错：触发条件是小模型能力不足又没触发升级条件；后果是用户拿到错误答案还一脸正常；防法是升级判定规则保守，宁可多升级一次也不放行可疑答案。
  • 自检本身也花钱：触发条件是自检靠再调一次小模型；后果等于又付一次小模型钱；防法是优先用免费的 JSON Schema 校验和关键词判断。
  • 难词表调参：触发条件是规则太宽或太窄；后果是全走强模型（省钱失效）或质量翻车；防法是拿样本集校准，和缓存阈值用同一批标注数据。
  • 模型迭代快：触发条件是把模型名写死在代码里；后果是便宜模型半年一换后接口失效；防法是 Bean 配置化，application.yml 里换名即可。

聊太久就写个小结翻篇（上下文压缩）

ConversationSummarizer + ChatWindow · 学术路线 LLMLingua-2 只调研不上线
推荐
一句话原理

多轮对话不能无限带全量历史——旧消息攒够阈值就调一次便宜模型压成一段摘要，之后只带「摘要 + 最近 2 轮原文」。另有一条学术路线是 LLMLingua-2（小模型先扫一遍 prompt 删冗余 token），本项目只做调研、不上实现，原因见「坑」第三条。

省多少

机制：把每轮输入钉死在「摘要 + 最近 N 轮」，不再随轮次线性增长。

量级：N=5、单轮 300 token、摘要 300 token 时，10 轮对话输入恒定约 1800 token，比全量带（约 3000+ token）省约 40%–50% 输入，轮次越多省得越多。推断 LLMLingua-2 论文端到端压缩比 2x–5x（粗到细框架可达约 15x），但它是 Python 库且会破坏厂商缓存前缀，只做调研。公开数据

Java 怎么落

库/组件：Spring AI 的 ChatMemory / MessageWindowChatMemory 现成窗口；自己写一个 Advisor 拦在 ChatClient 调用前，超阈值就调轻量模型生成摘要、替换旧消息。

要不要额外服务：不要。摘要时调一次 deepseek-flash 即可（输入 ¥1/M）。

关键设计：阈值用 jtokkit 数 token 而不是数消息条数；摘要 prompt 固定不动；摘要块放可变区（固定系统提示在前），保留厂商缓存前缀；摘要里必须写死出发地/目的地/时间/人数四个槽位。

可行性

纯 JVM 内规则，无向量、无 rerank、无 pgvector，和旧方案完全不同类；可 mock（本地写死一段摘要测管道）；换厂商零成本，逻辑全在 JVM 内。

怎么测
  • 灌 20 轮对话：发往模型的历史 token 永远 ≤ 阈值 + 单轮。
  • 摘要保槽位：金标断言摘要里仍保留出发地/目的地/时间/人数。
  • 最近 2 轮逐字保留：断言未被摘要吞掉。
  • 压缩 sidecar 关掉时：断言降级发原文、不抛异常。
坑
  • 摘要丢细节：触发条件是摘要 prompt 没写死槽位清单；后果是「我要带个 24 寸箱子」这类约束被压没，模型答非所问；防法是槽位清单写进摘要 prompt，并用金标单测对齐。
  • 破坏厂商缓存：触发条件是把摘要块放在固定前缀区、且每轮内容都变；后果是前缀不稳定、厂商缓存全废；防法是摘要块放可变区末尾，固定系统提示在前。
  • LLMLingua-2 互斥：触发条件是真跑本地压缩模型；后果是压缩位置每次不同毁掉前缀稳定，还要多养一个 560MB 的 Python 小模型，和旧项目气味重叠；防法是只做设计不做实现，简历写「调研后因与磁盘缓存互斥、中文压缩质量未验证而放弃」。

固定开头让厂商记住（前缀缓存 + 批处理）

StablePrefixBuilder / PromptLayoutStrategy · 配合 BatchJobScheduler
推荐
一句话原理

把 prompt 按「固定前缀在前、可变内容在后」组织：系统提示、工具定义、业务规则、输出 Schema 放最前，用户输入、工具返回、时间戳放最后；厂商发现两轮请求共享前缀就按 1 折左右收费。不急的离线任务打包走 Batch API，再打一个 5 折。

省多少

机制：重复前缀不再重复计费。DeepSeek 全自动磁盘缓存无需写代码，命中 ¥0.02/M vs 未命中 ¥1/M（官方定价页 2026-10-28），命中价是未命中的 1/50。公开数据

量级：Anthropic Sonnet 4.5 基准输入 $3/M、命中 $0.30/M（0.1x），5m 档「缓存一次再读一次就回本」；OpenAI GPT-6 系列共享前缀 30 分钟内复用最高 9 折；OpenAI 与 Anthropic 的 Batch API 全量 token 5 折，且折扣可与缓存叠加。公开数据 推断：GoShare 每轮复用 3k 前缀，叠前缀缓存后该部分省约 78%。推断

Java 怎么落

库/组件：StablePrefixBuilder 一个类负责拼固定区；Spring AI 已封装 Anthropic cacheOptions 与策略枚举；DeepSeek 侧零代码，只解析响应里的 prompt_cache_hit_tokens 字段做命中率看板。

要不要额外服务：不要。批处理可选——一张 batch_task 表 + @Scheduled 扫队攒批，演示时不接真厂商也能跑通状态机。

关键设计：把「打缓存点」抽象成自己的 PromptLayoutStrategy 接口，Anthropic 实现才插 cache_control 私有字段，别写死在业务代码里；业务规则文档打缓存点，每用户动态内容放最后。

可行性

DeepSeek 完全不用绑厂商（连开关都没有），换厂商不白干；学生充值 ¥10 够演示一下午；可 mock——断言发出去的请求前缀字节级相等即可，不必真打厂商。

怎么测
  • 前缀稳定：构造两轮请求，断言可变区之前的字节串逐字相等。
  • 缓存点位置：断言 cache_control 只打在 system/工具块，不打在用户消息上。
  • 命中率解析：响应 prompt_cache_hit_tokens > 0 时，断言按 0.1x 入账。
  • 无时间戳混入：扫描系统提示块，断言不含动态时间戳/随机 ID。
坑
  • 前缀动一个字缓存全废：触发条件是 Jackson 序列化把字段顺序打乱、或断点块里混入时间戳；后果是永远 miss、一分钱折扣拿不到；防法是做字符串 diff 断言 + 固定序列化顺序。
  • TTL 与流式耗时：触发条件是响应流了 4 分钟、下轮间隔超 5 分钟；后果是缓存过期、从头计费；防法是间隔大就换 1h 档（写入 2x，但读多次后回本）。
  • 绑定单厂商：触发条件是把 Anthropic 私有字段写死；后果是换 OpenAI/DeepSeek 后配置无效（不报错但不省钱）；防法是 PromptLayoutStrategy 抽象层。
  • 批处理时效性：触发条件是把实时匹配请求塞进批任务；后果是 24h 才交付、用户等到天荒地老；防法是批处理只接夜间离线任务，在线路径绝不过 BatchJobScheduler。

所有请求走一个门（网关与配额）

LlmGatewayFilter · 调研过 LiteLLM / New-API，本项目自建
推荐
一句话原理

在业务应用和各家模型之间架一层统一入口：Spring Cloud Gateway 加一个全局过滤器拦 /llm/**，所有 AI 请求必经它——识别场景、校验配额、按场景选模型档位、记账降级。开源界的 LiteLLM（Python）和 New-API（Go）是同类产品，但个人项目推荐自建：零依赖、好 mock、面试更能讲故事。

省多少

机制：本身不直接省 token，靠两条间接省——按场景降配（摘要/分类走 flash，撮合解释才走 pro），配额硬上限防代码死循环刷爆账单。

量级：配额拦截可把事故型账单直接归零（LiteLLM 虚拟 key 超预算即拒）。公开机制 按场景降配，推断可再省 20%–40%。推断

Java 怎么落

库/组件：Spring Cloud Gateway 过滤器 + Spring AI ChatClient 统一抽象 + Resilience4j 重试降级；埋点用 Spring AI 自带的 gen_ai.client.token.usage，自定义切面补 scenario / hit_layer / cost_cent。

要不要额外服务：不要。自建版零容器；LiteLLM 和 New-API（单容器 SQLite、中文控制台）作为「我调研过成熟开源方案」的对比谈资，不引入。

关键设计：每类场景用不同配额桶；重试只在 5xx/超时且最多 1 次（别对上游大请求重试，会翻倍烧 token）；网关独立成 gshare-llm-gateway 小模块，不散在各业务服务里。

可行性

外部依赖为零，MockWebServer/WireMock 模拟上游即可；演示时用 Actuator /actuator/prometheus 端点截图展示成本看板。

怎么测
  • 配额用完拦住：Mock 额度超限，断言请求不发上游、返回 429 或降级体。
  • 简单场景走便宜模型：断言 customer_qa 场景实际调用的是便宜那个 ChatModel。
  • 重试一次后兜底：上游第一次 500、第二次 200，断言上游被调 2 次；两次都 500 时走降级模板。
  • 记账金额对账：按响应 usage × 单价 = 期望值，误差 < 0.001 元。
坑
  • 自己写计费容易歪：触发条件是用本地估算当账、流式响应的 usage 没在最后一个 chunk 取；后果是账单对不上、面试被问穿；防法是真实口径一律取响应 usage 字段，jtokkit 只用于发请求前预检。
  • 网关成单点：触发条件是演示时网关挂了；后果是全链路挂；防法是本地重启策略 + 演示前 curl 健康检查，并保留业务侧直连降级开关。
  • 重试烧钱陷阱：触发条件是对大请求无脑重试；后果是 token 翻倍；防法是最多重试 1 次且只针对 5xx/超时。

其他四件顺手做的事

ParallelToolAdvisor / ToolResultTrimmer / VersionedAnswerCache / AnswerPrecomputeJob
推荐
一句话原理

四件不单独成体系、但叠起来很见效的小事：① function calling 合并并行（查订单、查行程、查规则一轮发完）；② 工具结果字段白名单裁剪（数据库查回 40 个字段，只挑 6 个塞给模型）；③ 精确匹配版本化缓存（按模型 + prompt 哈希 + 数据版本精确命中，0 token）；④ 离线预计算 FAQ 答案（定时任务提前生成，线上读库）。

省多少

机制：Anthropic 官方「缓存 + 保持中间结果不进上下文」改造后，复杂研究任务平均 usage 从 43,588 降到 27,297 tokens，降 37%；学术侧并行化函数调用降约 40% token。公开数据

量级：字段白名单单次工具结果省约 85%；精确命中与预计算读时 token 100% 归零；预计算覆盖 60% 请求时，整体平均 token 直降 60%。推断

Java 怎么落

库/组件：ToolResultTrimmer（Jackson 白名单序列化）、ParallelToolAdvisor（Spring AI parallel tool calls）、VersionedAnswerCache（Caffeine + t_llm_answer_cache 表，key = sha256(模型 + 归一化 prompt + 版本号)）、AnswerPrecomputeJob（@Scheduled 凌晨跑）。

要不要额外服务：都不要，纯 JVM。

关键设计：白名单每个工具配一张金标单测；预计算绑数据版本号事件（政策一改即时重算），不纯靠定时；预计算只覆盖高频标准问题，个性化追问走实时。

可行性

全部零外部依赖、可 mock，测试最好写；预计算演示直接对比「实时生成 2s vs 预计算 5ms」，视觉冲击强。

怎么测
  • 三个无依赖工具一轮并行：断言模型只发 1 次请求，而非 3 次串行往返。
  • 白名单只留声明字段：喂一条 40 字段 JSON，断言输出字段集 == 白名单集合。
  • 版本变了缓存作废：规则文档 v1→v2 后，断言同 prompt 重新回源。
  • 读路径零调用：读 FAQ 接口时，断言 mock 上游 0 调用。
坑
  • 白名单漏字段：触发条件是 DTO 少写一个模型需要的列；后果是模型瞎编（幻觉）；防法是每个工具配金标单测对齐，且错误信息/异常栈永不裁剪。
  • 预计算数据过期：触发条件是政策改了没触发重算；后果是演示时答旧规则（事故）；防法是版本号事件驱动重算，不只靠 cron。
  • 并行工具失效：触发条件是便宜模型不会并行、拆成两轮；后果是省钱失效还多花一轮；防法是演示前固定模型版本，失败时退回串行也不报错。

三套组合架构单点手段有限，叠起来才有量级

三套架构不是三选一，而是按顺序叠着做：甲是省钱流水线（先做，把结构定下来），乙是离线预计算（再做，把数字做漂亮），丙是统一网关（收尾，把故事讲圆）。推荐顺序甲 → 乙 → 丙——甲不定下来，乙和丙的收益都没法度量。

方案 甲：省钱流水线（基线，零外部服务，先做这套）

适合：第一批落地 · 代码量约 3–5 天 · 额外服务：无

数据流

第 1 步问题清洗：去空格、统一全半角，算「问题指纹」
→
第 2 步查版本化缓存，命中直接返回（0 token）
→
第 3 步未命中，免费小模型先答（固定前缀）
→

→

第 6 步记账写 t_llm_call_log，按指纹回填缓存

命中路径（最省钱的那条）

第 1→2 步直接返回。用户看到的是「秒回」，后台成本 0。

降级路径（出问题怎么兜）

三道兜底：模型超时/报错 → 返回预生成的兜底答案；连续失败 → 熔断，只走缓存 + 转人工；配额到顶 → 降配到免费模型，并在回复里标注「当前为简易回答」。

成本估算

假设 1000 次/天、每次输入 2000 token、输出 300 token。基线（每次全量调 pro）：2000×3e-6 + 300×6e-6 = ¥0.0078/次 → ¥7.8/天。甲套：40% 命中缓存（0 元）；剩余 600 次里 420 次走 flash：2000×1e-6 + 300×2e-6 = ¥0.0026/次 → ¥1.09；180 次升级 pro → ¥1.40，合计 ¥2.49/天、省 68%。再叠固定前缀命中（按 1200 token 稳定前缀，420 次各省 1200×(1e-6−0.02e-6) = ¥0.0012）再省 ¥0.50 → 约 ¥1.99/天、省约 74%。推断，非实测

优点 / 代价

优点：不需要任何额外容器、全部可 mock、四层结构一眼能讲清。代价：真要跑起来需要模型 key（可用免费额度兜）。

落到三个 AI 功能A1 搜行程、B1 工单、A2 取消挽留

三个功能按同一思路配层：结构化输出减少来回、高频内容缓存或预计算、数字一律不让模型算。A1 重点是「口语解析 + 解释缓存」，B1 重点是「分类前缀 + 摘要窗口」，A2 重点是「代码算钱 + 话术池」。
功能用户看到的样子省钱关键点落到哪个类
A1 搜行程 + 智能撮合 说一句「明天早上八点从裕华路去正定机场，两个人」，直接出符合条件的行程 ① 结构化输出一次成型，把「口语→查询条件」一轮搞定，不走多轮追问；② 口语解析结果按指纹缓存，同样的话第二次直接命中；③ 真正搜行程走 MySQL/ES，不让模型生成行程列表；④ 撮合排序用规则打分，模型只解释「为什么推荐这个」。 TripQueryParser（解析）+ TripRanker（规则排序）+ TripExplainCache（解释缓存）
B1 工单分派 + 会话摘要 + 回复草稿 用户提交工单，自动归到「支付问题/司机迟到」等类别，附带三行摘要和一段可直接发的回复 ① 分类规则文字固定成前缀，让厂商缓存记住；② 分类用免费/最便宜模型（这道题不难）；③ 摘要只喂最近 5 条消息 + 工单标题，长对话先揉成 200 字摘要；④ 草稿先查模板库，命中就改写，不从零生成。 TicketClassifyService + ChatSummaryService + ReplyDraftService
A2 取消挽留 + 退改费用解释 用户点取消，先看到「退你多少钱、为什么」，再看到一句挽留话术 ① 金额一律用 Java 代码算（FeeCalculator 纯函数，可单测），模型只把结果说成人话——既省 token 又不会算错；② 挽留话术从预生成池里按场景取，个性化只做一句话微调；③ 费用解释模板固定前缀。 FeeCalculator（算钱）+ FeeExplainer（解释）+ RetainScriptPool（话术池）

关键取舍：数字不让模型算

这是省 token 里最「便宜」的一条，也是最防翻车的一条，面试必讲：退多少钱、优惠几元，一律由 FeeCalculator 纯函数算好，模型只负责把算式结果翻译成人话。

怎么算"省了多少"

公式：

单次成本 = 输入token/1e6 × 输入单价 + 输出token/1e6 × 输出单价
节省比例 = 1 − (新方案总成本 / 基线总成本)

算例（按 2026-10-28 官方价、假设 1000 次/天）：基线 ¥7.8/天 → 甲套（叠固定前缀命中）¥1.99/天 → 省 74.5%。推断

口径纪律：token 一律取响应里的 usage 字段，不用本地估算值；jtokkit 只用于发请求前的预检（例如 prompt 超 6k token 就拦截、改走裁剪）。

对比实验怎么跑

  • 样本：100 道真实问题（A1/B1/A2 各抽 30+，另取 10 道边界），从演示工单/公开测试集取，不自己编。
  • 分组：A 组走基线（每次全量调 pro），B 组走新链路；同一批问题、同一时间窗、顺序随机，避免上下文污染。
  • 指标：总 token、总成本、平均耗时、答案合格率（人工或强模型按 1–5 打分，≥4 算合格）。
  • 护栏：合格率下降 ≤ 2 个百分点；超过就调阈值/缩小缓存范围，否则省的 token 不成立。
  • 产出：一张 4 列对比表 + 一条 SQL 出的成本日报（面试直接放截图）。

# GoShare 阶段 4 压测报告

> 验收口径：**不超卖 + 有压测报告**。本文档为阶段 4 唯一压测交付物。
> 日期：2026-10-30（本地单机环境）

## 1. 压测目标与环境

| 项目 | 说明 |
|---|---|
| 被测系统 | GoShare 顺风拼车（Spring Boot 3.2 + Spring Cloud Alibaba 微服务） |
| 压测工具 | Apache JMeter 5.6.3（非 GUI 命令行模式） |
| 压测机 | 单机（Windows），与被测服务同机 |
| 中间件 | docker-compose 容器：MySQL / Redis / RocketMQ / Nacos |
| 被测业务 | 行程 tripId=2「石家庄→北京，60 元，3 个座位」并发下单 |

压测数据隔离方式：每次压测前重置 `trip:seats:2`（Redis 座位库存 = 3）与 DB `remain_seats=3`；每个线程使用唯一幂等键（JSR223 动态生成），避免历史数据干扰、可精确统计实际建单数。

## 2. 场景 A：并发抢座不超卖（直连订单服务 8003）

- 脚本：`jmeter/jmeter-sceneA-nosellout.jmx`
- 配置：**50 线程**，ramp-up 3s，每线程 1 次下单（seatCount=1），直连 `localhost:8003`（绕过网关限流，专门验证库存不超卖）
- 结果（jtl 统计）：

| 指标 | 数值 |
|---|---|
| 总请求数 | 50 |
| HTTP 200 响应 | 50（100%） |
| 请求失败（网络/5xx） | 0 |
| RT avg / p50 / p95 / max | 1483ms / 1752ms / 2735ms / 2902ms |

- **DB 后置条件（判定依据）**：

| 检查项 | 结果 |
|---|---|
| 实际建单数（唯一幂等键落库） | **3** |
| 行程余座 remain_seats | **0**（3 − 3） |
| 超卖（建单数 > 可用座位） | **否，未超卖** |
| 服务端异常（ERROR 日志） | 0 |

- 说明：50 个请求全部被受理（HTTP 200），其中 3 个成功建单、47 个被余票防线拒绝（业务码 400「余票不足」）。高并发下同一行程的 Redis Lua 扣减与 DB 事务存在锁竞争，RT 被拉高（p50 1.7s 属正常排队现象）；不超卖的最终证据是 **DB 建单数 = 3 ≤ 座位数 3**。

## 3. 场景 B：网关限流（走统一入口 8000）

- 脚本：`jmeter/jmeter-sceneB-gateway-limit.jmx`
- 配置：**100 线程**，ramp-up 2s，每线程 1 次下单，走 `localhost:8000`（网关 → Sentinel 令牌桶限流：单 IP 20 qps / 突发 40 → 订单服务）
- 结果（jtl 统计）：

| 指标 | 数值 |
|---|---|
| 总请求数 | 100 |
| HTTP 429（Too Many Requests，被限流） | **60（60%）** |
| HTTP 200（放行到业务层） | 40 |
| RT avg / p50 / p95 / max | 670ms / 655ms / 863ms / 885ms |

- 说明：100 个突发请求超过限流阈值（突发 40），网关层按令牌桶规则拒绝 60 个（429），40 个放行进入业务层。放行的 40 个请求到达订单服务后仍受余座防线约束（该轮压测前余座已被场景 A 耗尽，40 个全部被「余票不足」拒绝），**未产生任何超卖**。限流本身按预期生效。

## 4. 结论

1. **不超卖达标**：并发 50 抢 3 座 → DB 建单 3、余座 0、无负库存、服务端无异常。防超卖由「Redis Lua 原子扣减 + DB 条件更新 remain_seats + 唯一幂等键」三层共同保证。
2. **网关限流生效**：100 突发 → 60 个 429 被拒，放行流量再进业务防线，多级防护闭环。
3. **RocketMQ 延时消息超时释放链路验证（2026-10-30 实测）**：下单（14:28:59）→ 发送延时消息（原生 Message，Tag=`ORDER_TIMEOUT`、delayLevel=14 对应 10 分钟档）→ 消息 14:38:59 到期进入 `GO_SHARE_ORDER` 并被消费者拉取（mqadmin 实证 `Tags:[ORDER_TIMEOUT]`、`MessageTrack=CONSUMED`，此前 Tag 失效时是 `Tags:[null]+CONSUMED_BUT_FILTERED`）→ 订单状态 CREATED→EXPIRED、Redis 消费去重键 `order:timeout:consume:{orderNo}` 出现（防重复）、余座回补（Redis/DB 均回 3）。兜底定时扫描（12 分钟，比延时消息晚 2 分钟）在消息路径异常时仍可关单（历史验证过）。

## 5. 复现方式

```powershell
# 1) 重置被测行程余座（Redis + DB）
redis-cli set trip:seats:2 3
docker exec goshare-mysql mysql -uroot -proot123 -e "UPDATE goshare.trip SET remain_seats=3 WHERE id=2;"

# 2) 登录拿 token，替换 jmx 中的 __TOKEN__ 占位生成 _run.jmx
# 3) 场景 A（直连 8003）
jmeter.bat -n -t _work\jmeter-sceneA-nosellout_run.jmx -l _work\sceneA.jtl -f -j _work\jmeter-sceneA.log

# 4) 场景 B（走网关 8000，建议先重置余座）
jmeter.bat -n -t _work\jmeter-sceneB-gateway-limit_run.jmx -l _work\sceneB.jtl -f -j _work\jmeter-sceneB.log

# 5) 核对：实际建单数（幂等表）+ 余座
docker exec goshare-mysql mysql -uroot -proot123 -N -e "SELECT COUNT(*) FROM goshare.idempotency_key WHERE idempotent_key LIKE 'CREATE_ORDER:jmeter-%'; SELECT remain_seats FROM goshare.trip WHERE id=2;"
```

> 注：jtl 结果文件与 `_run.jmx`（token 已替换）为 `_work` 临时产物，不入库；正式入库的是 `jmeter/*.jmx` 脚本与本文档。
